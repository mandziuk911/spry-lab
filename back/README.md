# Backend

The active API is unauthenticated `GET/POST /api/meetings` and `GET /api/health`.
Meeting UUIDs are generated by PostgreSQL. Health reports database readiness.
Storage failures roll back and return generic 503 responses; POST is never retried.
Connections/pool acquisition and server queries have bounded timeouts.

## Checks

From `back/`, with Python 3.12.10 and uv 0.6.17:

```sh
uv sync --frozen
uv run --frozen ruff check .
uv run --frozen ruff format --check .
uv run --frozen pytest
```

Without `DATABASE_URL`, PostgreSQL integration tests are explicitly skipped;
validation, routes and simulated storage-error tests still run. Set `DATABASE_URL`
to a **dedicated test database**, e.g.
`postgresql+psycopg://spry:spry@localhost:5432/spry_test`, for all tests.
Conftest creates a uniquely named disposable schema per integration test and
runs the real Alembic migrations there. It never uses `create_all`, drops public
tables, or migrates the application schema. The test database user needs schema
creation privileges. Do not point tests at the Compose application database.

The image installs the frozen production lock, then runs `alembic upgrade head`
before serving Uvicorn. Migration failure prevents startup. No seeding occurs.

## Migration review / backup required

Revisions 0001–0003 are preserved unchanged. Revision 0004 keeps all meeting
UUIDs, titles and timestamps, backfills `attendee_count` from association rows
(including zero for meetings without participants), then drops participant/user
tables and legacy meeting metadata/ownership columns. Nonnegative count and
positive duration are enforced in PostgreSQL. Invalid legacy durations cause
an atomic migration failure; inspect and correct them deliberately before retrying.

**0004 is irreversible.** Counts cannot restore identities, associations,
users, ownership, descriptions, locations, links or audit timestamps. Its
downgrade always raises before any schema/data mutation, including on empty
meeting tables: deleted directory/user records cannot be inferred. Return to
0003 only by restoring a pre-upgrade backup, not by `alembic downgrade`.
Review this destructive migration separately before running it on valuable data.
