# ADR 0008: Run Spry's core on Google Cloud without moving the AWS integrations

**Status:** Lab 9 decision; no-account route. The GCP infrastructure and deployment instructions are a draft, not a deployed environment.

## Context and decision

Move the static React frontend, FastAPI meeting API and PostgreSQL schema together. Keep the database on the same cloud and in the same region (`us-central1`) as the API. The AWS column below distinguishes the course's serverless reference from this fork's ECS/Fargate and RDS setup. The GCP deployment has its own data and is not an active-active replica or a replacement for AWS.

| Spry on AWS | GCP candidate | Decision for Spry and what changes |
| --- | --- | --- |
| S3 + CloudFront (Free plan reference) + WAF | Firebase Hosting | **Replace** for the GCP frontend. Publish Vite's static `dist/` with CDN and managed HTTPS; use the Cloud Run origin as API base and allow the exact Hosting origin in CORS. Hosting does not replace the existing AWS WAF/origin policy; an unadorned Cloud Storage bucket is not equivalent HTTPS hosting on a custom domain. |
| Lambda + function URL (lab reference); ECS/Fargate + ALB (this fork) | Cloud Run | **Replace** the core API. Run FastAPI as an HTTP container listening on `$PORT`, without Lambda Web Adapter or Mangum. Use request-based billing and zero minimum instances. The draft restricts invocation to named GCP principals; direct browser access from Firebase requires a separate decision. Any browser-accessible path must retain the app's Cognito access-token check for meeting endpoints. |
| ECR | Artifact Registry | **Replace** for the GCP image. Keep it regional and publish a versioned image; retained versions use the registry storage quota. |
| Aurora Serverless v2 (lab reference); RDS PostgreSQL (this fork) | Cloud SQL for PostgreSQL | **Replace** for the GCP copy: Enterprise, zonal `db-f1-micro`, 10 GB SSD. Use the Cloud SQL attachment and a least-privilege runtime service account. Preserve Alembic migrations, joins and constraints. Initialize a fresh lab database with those migrations, not a production data export. |
| DynamoDB (hypothetical SQL replacement) | Firestore | **Drop** this option. No idle instance charge, but reads, writes, storage and indexes affect billing; adopting it would replace SQL joins, constraints and migration/data-access logic with document models and query-specific denormalization. |
| Cognito user pool + Google | Identity Platform / Firebase Authentication | **Keep** Cognito. The frontend and Cloud Run API retain the existing sign-in and access-token verifier; register new callback/logout URLs if actually deploying. An Identity Platform migration would need new client/token validation and an account migration or relinking plan. |
| EventBridge Scheduler | Cloud Scheduler | **Keep** the AWS weekly trigger with the rest of the pipeline. Cloud Scheduler could call a Cloud Run handler with an authenticated HTTP request; no GCP job is needed for the core. |
| SQS request queue + DLQ | Pub/Sub or Cloud Tasks | **Keep** SQS with the report builder. Pub/Sub push is appropriate for fan-out; Cloud Tasks is closer to a rate-controlled work queue. Either migration must preserve retry, idempotency and failed-work handling. |
| S3 report event → Lambda mailer | Cloud Storage + Eventarc → Cloud Run | **Keep** the AWS trigger and report bucket. A GCP replacement would need a new object-event handler, regional/identity configuration and duplicate-event handling. |
| SES | No direct managed equivalent; third-party email API or SES | **Keep** SES with the AWS mailer. It uses a scoped Lambda IAM role and short-lived credentials, so there is **no email API key** to store. If a future GCP mailer uses an external provider, keep its key in Secret Manager, accessible only to that mailer's runtime identity. |
| Bedrock (Nova/Claude) | Vertex AI (Gemini; Claude via Model Garden) | **Keep** the AWS parser and its model/prompt/validation contract. No Vertex AI spend or model change is needed to read meetings; a later move needs quality, latency and token-price evaluation. |
| SSM Parameter Store / Secrets Manager | Secret Manager | **Replace** for GCP database credentials only. Generate the password in Terraform and inject the database connection secret at runtime. Secret payloads can also exist in Terraform state; restrict, encrypt and never commit it. |
| CloudWatch Logs | Cloud Logging | **Replace** for Cloud Run logs. Use container stdout/stderr; do not log tokens or credentials. Review retention and ingestion separately from the AWS pipelines. |
| IAM roles | Service accounts + IAM roles | **Replace** on GCP. Separate deploy and runtime identities. Give the runtime Cloud SQL Client and access only to its connection secret. Use local ADC or short-lived Workload Identity Federation (restrict CI trust to the intended repository/owner IDs); no JSON keys. |
| Terraform AWS provider | Terraform Google provider | **Replace** for `gcp/`. Keep `infra/` and `gcp/` as independent roots and states; use a separate protected workspace if managing the GCP stack in HCP Terraform. Never reuse the AWS state. |

## Database trade-off and operational consequences

- **Cloud SQL running for the demo period (chosen):** same-region queries and minimal application changes; predictable capacity cost even on an empty day. A shared-core micro is for this small zonal lab, not a high-availability production sizing claim.
- **Stop Cloud SQL outside demos:** the same code and query latency once running, but the API cannot read or write while it is stopped. Start it before a session and wait for readiness. Storage, retained backups and assigned idle public IPv4 can still cost money; there is no automatic resume on a request.
- **Firestore:** attractive for a quiet app with no relational needs. No instance cold-start after a scheduled stop and no hourly DB compute, but fan-out, additional reads and denormalized writes can cost more than a simple estimate; it is not a SQL drop-in.
- **Query RDS/Aurora across clouds:** preserves SQL and avoids a second database, but every DB round trip gains WAN latency, AWS outbound traffic may incur egress, and exposing or privately connecting to RDS adds networking cost and failure modes. Do not open the AWS database to the internet to make this work.

The weekly report stays tied to AWS's data: it will not read the independent GCP database. The optional parser is database-independent and could be wired across clouds only with its existing token/CORS rules; the core build does not depend on it. Cognito remains a dependency for login/token renewal and signing-key refresh, not a cross-cloud request for every SQL query.
