# ADR 0007 — Terraform для інфраструктури Spry

**Статус:** запропоновано; міграцію не виконано і рішення ще потребує погодження.

## Контекст

У репозиторії є CloudFormation-шаблони для auth, backend, frontend, reports та AI. Локальні `infra/versions.tf`, `auth.tf`, `reports.tf`, `ai.tf` — чернетки Terraform, а не доказ керування ресурсами. Вони охоплюють лише частину інфраструктури; фактичний склад і власність AWS-ресурсів у цьому сеансі не перевірялися. `versions.tf` вимагає Terraform >= 1.10 та AWS provider ~> 6.0; регіон за замовчуванням — `eu-north-1`, AI — `us-east-1`. Локальні `terraform fmt -check` і `terraform validate` проходять із AWS provider 6.71.0; перевірка фактичного стану не проводилася. Backend не налаштований.

## Запропоноване рішення

Після погодження поступово передавати відповідальність за вибрані ресурси від CloudFormation до Terraform, з віддаленим state в окремому HCP Terraform workspace, захищеним доступом і блокуванням конкурентних операцій. Організація та workspace ще не вибрані, підключення не налаштоване. До готовності backend та інвентаризації **не виконувати apply**. CloudFormation залишається поточним описом розгортання, але фактичний стан треба окремо підтвердити. Альтернативи: залишити CloudFormation або погодити захищений S3 backend із блокуванням; вибір HCP ще не є виконаним переходом.

## State і секрети

Без налаштованого backend Terraform за замовчуванням використовує локальний state; це непридатно як спільне джерело істини і легко призводить до витоку чи конфліктів. Навіть `sensitive = true` лише приховує значення у звичайному виводі, а не шифрує чи прибирає його зі state або збережених plan. У чернетці `auth.tf` Google OAuth client secret може потрапити в state; `reports.tf` читає Secrets Manager і передає `DATABASE_URL` у Lambda environment, тому значення також може бути у state та plan. Ротація в Secrets Manager сама по собі не оновить уже передане Terraform значення в Lambda. Перед впровадженням розглянути отримання секрету застосунком під час виконання, мінімальні IAM-права, ротацію та обмеження доступу до Lambda. Не записувати секрети, state, plan чи токени до Git або звіту; зберігати резервні копії зашифрованими з обмеженим доступом, визначити політики доступу, аудиту й зберігання. HCP sensitive variables також не усувають ризик секретів у state.

## Безпечна міграція (майбутня)

1. Узгодити scope, відповідальних, акаунт/регіони, резервне копіювання і rollback; перевірити автентифікацію, поточні CloudFormation stacks, залежності, outputs, параметри та реальні ресурси лише читанням. Не припускати, що кожен ресурс існує.
2. В окремому тестовому середовищі перевірити чернетки із зафіксованою версією провайдера, а також відповідність шаблонам і живим налаштуванням. Жоден із цих кроків сам по собі не доводить безпечність production.
3. Створити погоджений HCP workspace і налаштувати backend, доступ, блокування, credentials та безпечні змінні. Переконатися у виборі правильного workspace; зробити захищений backup наявного state, якщо він існує. Перенесення наявного state проводити лише після перевірки джерела і призначення та відповідним `terraform init -migrate-state`, не перезаписуючи чужий state.
4. Для кожного ресурсу зафіксувати точну адресу Terraform і фізичний ID, можливість імпорту, залежності й правила retention. Призупинити зміни та CI обох систем. Узгодити безпечне виведення ресурсу з управління CloudFormation із збереженням фізичного ресурсу (наприклад, підтримуваний retain/stack refactoring, де застосовний); перевірити результат для кожного типу. Не видаляти stack навмання. Не допускати одночасного управління двома системами і не застосовувати неперевірений план. Імпорт Terraform сам по собі не передає власність від CloudFormation.
5. Імпортувати лише перевірені існуючі ресурси у правильний state; неіснуючі розглядати окремо. Особливо перевірити Cognito pool і дані, S3 bucket та його єдину конфігурацію notifications, IAM, зв'язки SQS/Lambda, scheduler і DB-доступ. `prevent_destroy` у чернетках не є повною гарантією збереження.
6. Створити та ретельно переглянути plan з реальними значеннями без публікації секретів; усунути drift і зупинитися на будь-якому неочікуваному create, delete або replacement. Застосовувати лише окремо погоджений план у погоджене вікно; перевірити сервіси, state і моніторинг. Визначити перевірений rollback без повторного створення або втрати даних; не відновлювати старий state поверх новішого без аналізу lineage/serial та фактичних ресурсів.

## Обмеження та наслідки

Публічна сторінка HCP Terraform у цьому сеансі відповіла HTTP 200 після перенаправлення на login, але авторизований доступ до організації/workspace не перевірявся: для цієї лабораторної HCP workspace недоступний/не налаштований, а не доведено глобальний збій HCP. Реальних імпортів, remote state, plan, apply, live-перевірок або переходу власності не було. Міграція потребує часу, доступів і контролю секретів; усунення drift може змінити ресурси, тому потребує окремого погодження.
